# NovaHub 安全与隐私

## 1. 威胁模型

需要防御的主要风险：恶意或被攻陷的插件、畸形插件包、无限计算与内存消耗、权限逃逸、敏感信息泄漏、IPC 冒充、更新供应链攻击和本地数据被其他低权限进程读取。

MVP 不承诺抵御已获得管理员/root 权限或完全控制当前用户会话的攻击者，但必须遵循最小权限并减少可利用面。

## 2. 信任边界

```text
可信：签名的 NovaHub 主程序、Plugin Manager、数据库迁移
受限可信：Plugin Host 进程与 Wasmtime
不可信：所有第三方 WASM、插件资源、网络响应、导入包
外部系统：OS API、系统索引、凭据存储、更新源
```

来自插件和网络的数据必须在进入 UI、日志、文件系统或数据库前验证。

## 3. 插件沙箱

- WebAssembly Component 不继承宿主环境变量、stdio、目录或 Socket
- 不预开放通用 WASI；只链接 NovaHub 明确提供的 WIT 能力
- 每个插件独立 Store、内存限制、fuel/epoch、deadline 与资源表
- Host API 每次调用重新校验插件身份、权限和参数，而非只在安装时校验
- URL 规范化后匹配 HTTPS Origin，并对 DNS 重绑定、重定向和本地/保留地址进行防护
- 文件句柄由宿主生成且与插件绑定，路径字符串不能替代句柄
- View 输入进行深度、数量、长度、Markdown 和资源校验
- 插件日志在 host side 按字段策略过滤；插件自报的敏感等级只能收紧记录范围，不能绕过宿主过滤

### 3.1 权限授权模型

manifest 中的 `DeclaredPermission` 与运行时的 `EffectiveGrant` 是不同安全对象：

```text
EffectiveGrant = DeclaredPermission ∩ UserGrant ∩ HostPolicy
```

- 清单解析必须保留结构化 scope；未知能力、未知字段、非法或超限 scope 默认拒绝。
- HTTP 只接受规范化 HTTPS Origin；文件清单只表达 `user-selected` 意图，运行时只接受宿主签发且绑定插件身份的 handle；Clipboard 读写分权。
- 用户授权不能扩大声明，宿主策略不能被声明或用户选择绕过；撤销授权后，既有会话的后续调用也必须失败。
- UserGrant 使用独立、有界的宿主 `SQLite` 记录；缺失记录仅用于首次安装审批初始化，显式空记录表示全部撤销，重启后仍保持撤销状态。
- 插件更新新增或扩大权限时复用旧 UserGrant 并与新声明求交集；只有用户再次明确批准后才能获得新增能力。
- Capability Broker 每次调用重新校验插件身份、有效授权和具体参数。SDK 本地 `require` 只改善错误信息，不是安全边界。
- 发布者 `reason` 仅用于解释且必须标注来源，不参与权限计算。
- MVP 不引入路径 glob、任意 shell、环境变量、原始 Socket、后台任务或通用 deny/allow 字符串策略语言。

## 4. 包与供应链

- 归档解压防路径穿越、符号链接逃逸、压缩炸弹和重复文件覆盖
- 清单、WASM 与资源全部包含在签名范围
- 插件发布者使用 Ed25519 密钥；市场阶段再增加身份验证和撤销机制
- NovaHub 应用签名、更新元数据签名和插件发布密钥使用不同密钥与用途标识；发布流程记录 key ID、有效期、轮换窗口和撤销状态
- 密钥轮换必须允许新旧公钥短期重叠验证，并通过受保护版本发布新信任集；私钥不进入源码、普通 CI 日志或开发者工作站共享目录
- 官方二进制生成 SBOM，依赖执行许可证和漏洞扫描
- CI 固定 Rust 工具链与关键依赖版本，发布从受保护标签产生
- 安装包校验失败一律拒绝，不提供“仍然安装”按钮；开发者模式是独立路径

MVP 的插件信任摘要只使用宿主本地已校验的 publisher key ID、归档 SHA-256、签名状态、插件 API 兼容性和开发者模式状态。source repo、source commit、builder identity、workflow、SBOM digest 和 transparency log reference 属于 Phase 2 扩展 provenance；只有进入签名范围并完成对应校验后才能显示为“已验证”，包内自报值最多显示为“未验证声明”。

## 5. 应用签名与更新

- Windows 二进制和安装包使用代码签名证书，更新校验签名与哈希
- macOS 使用 Developer ID、Hardened Runtime、Notarization 和 Stapling
- 更新元数据使用独立签名并防回滚到低于安全最低版本
- 下载到 staging 后校验、安装、健康检查，再切换版本
- 更新失败恢复旧版本；数据库迁移与应用更新要有兼容窗口

## 6. 本地数据保护

- 数据目录权限限定当前用户
- 剪贴板和插件 Secret 加密，密钥存系统凭据存储
- 剪贴板载荷使用宿主 AEAD 加密并受默认 500 条、单项大小和 7 天 TTL 限制；用户只能在宿主允许的范围内调整保留策略，密钥获取失败时拒绝写入，不回退到明文或固定密钥
- 崩溃报告和诊断包默认本地生成，发送前展示包含内容并允许删减
- 插件生命周期诊断使用默认 256 条的有界环形缓冲区，字段长度受限；不记录查询输入、文件内容、完整 URL 或插件表单值
- 设置提供“暂停剪贴板”“清空历史”“删除全部本地数据”入口
- 卸载插件默认删除其本地存储、Secret、缓存、权限和索引
- 应用卸载器是否删除 NovaHub 全部用户数据必须由用户明确选择，不能隐式删除

## 7. 隐私策略

MVP 默认无遥测、无账号、无云端。若未来引入遥测：

- 必须显式选择加入
- 事件采用数据字典，不允许任意属性
- 不收集查询、剪贴板、文件名、插件表单内容或完整 URL
- 提供本机查看、导出和撤回
- 产品功能不能依赖用户同意遥测

## 8. 权限 UX

权限提示必须说明：插件是谁、请求什么能力、允许的具体范围、为什么需要、拒绝后哪些功能不可用。安装/更新必须区分新增、扩大、收窄、移除和未变化；新增或扩大权限不能在静默更新中获得，拒绝时保持旧 active pointer。

网络权限展示 Origin 列表；文件权限展示选定目录或文件；剪贴板读写分开。发布者 `reason` 明确标为“发布者说明”，不能伪装成宿主背书。MVP 不提供永久“所有文件”权限。

MVP 的原生 Shell 管理入口为 `plugin permissions <id>`、`plugin revoke <id> [capability|all]`
和 `plugin approve <id>`。撤销与重新批准都在主进程完成，不启动 Plugin Host。

## 9. 安全测试

- 插件包 fuzz、WIT 解码 fuzz、View/Markdown fuzz
- IPC 长度、认证、重放、乱序和断连测试
- SSRF、重定向、DNS 重绑定和 URL 规范化测试
- 文件句柄越权、符号链接和 TOCTOU 测试
- Wasmtime 超时、内存、资源表泄漏与大量会话压力测试
- 数据库损坏、迁移回滚、密钥缺失与凭据删除测试
- Windows/macOS 签名、权限和升级/降级测试

## 10. 响应与撤销

建立插件哈希和签名撤销列表，但 MVP 本地安装模式下只能在用户更新 NovaHub 或主动刷新安全元数据后生效。撤销后默认禁用插件并解释原因，不在未确认时删除用户外部文件。

严重宿主漏洞需要最低安全版本策略、发布公告和更新迁移路径。安全修复不得通过扩大云端依赖或收集更多用户数据实现。
